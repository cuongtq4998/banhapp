# Place Order UI, part 13: Order tracking by phone (screens S-10, S-11)

Part of the split UI specification; index: [place-order-ui.md](../place-order-ui.md). Version 1.1 [v1.1 | 2026-11-02] (fee block states, see S-11; v1.0 owner approved 2026-11-02). Status: owner approved 2026-11-02. Based on `product/place-order.md` v1.10 and `product/place-order/08-order-tracking.md` [v1.0 | 2026-11-02]. Traces: FR-22 to FR-27, BR-16 to BR-18, AC-38 to AC-47, FR-28 to FR-30 (AC numbers as in the PRD part; scribe confirms). API: `api/10-customer-order-lookup.md` v1.3 (`POST /v1/orders/lookup`), ADR-0034. Copy and accessibility: [part 14](14-order-tracking-copy-a11y.md). Fake data only.

## S-10 Track orders (entry and phone entry)

- Purpose: the customer sees where their orders are, with no sign-in and no push. [v1.0 | 2026-11-02] Entry (owner decision): a "Theo dõi đơn" row (`T_TRACK_ENTRY`) on the HOME screen S-2, and the "Follow this order" button on the confirmation screen S-9. The menu is not used. Exit: back.
- Layout: `TopBar` `T_TRACK_TITLE`; short line `T_TRACK_HELP` (enter the phone number used to order); `TextField` `T_F_PHONE` (phone keyboard, label above, autofill off, the field keeps the last phone typed during the session only, in memory; nothing is stored on the device by the app); `PrimaryButton` `T_TRACK_SUBMIT`. The phone is normalised by the server (spaces, dots, leading 0). [v1.0 | 2026-11-02] The client check (9 to 11 digits after cleaning) is only a hint: it shows `T_ERR_PHONE` early but the server decides; the 422 `VALIDATION_FAILED` for the phone field shows the same text. Nothing is searched while typing.
- Home entry [v1.0 | 2026-11-02]: the S-2 row is a secondary row under the main order action, opens S-10 with an empty phone field (or the phone held in memory from this session). Test id `order.track.entry`.
- Privacy line `T_TRACK_PRIVACY` under the field: only the masked phone and district are shown. The screen never shows name, street or note.
- From the confirmation [v1.0 | 2026-11-02]: S-9 has a secondary button `T_FOLLOW_ORDER` (see 5.9); it opens S-10 with the order's phone already filled, held in memory only (cleared with the flow data, never stored or put in navigation state beyond the in-memory value), and runs the lookup at once.
- States: Default (field, button); Loading (button spinner, field disabled); Error (field error `T_ERR_PHONE`); Offline (`T_OFFLINE`, button stays, no request); Rate limited, see S-11.

## S-11 Track orders, result list

- Layout: below a sticky summary line `T_RESULT_FOR` with the masked phone (`+84 900 000 ***` as sent by the server); list of order cards, newest first (`placed_at` descending); pull to refresh (native `refreshable` / Material pull-to-refresh) reruns page 1; the list shows `T_AS_OF` (the server `as_of` time) at the bottom of the page; [v1.0 | 2026-11-02] `as_of` is also the "data as of" value shown offline (`T_STALE_AS_OF`).
- Paging: 10 per page, at most 5 pages. The next page loads when the person reaches the end (a `T_LOAD_MORE` row with spinner; on failure the row becomes the retry button `T_RETRY`). After the last page (no cursor), if 5 pages were loaded the line `T_LIST_END_LIMIT` says that the newest 50 are shown and the shop can help with older ones (with shop contact); otherwise nothing.
- Order card [v1.0 | 2026-11-02] (owner decision: each card shows the order code and the cake names with quantities, nothing more about the person): `T_ORDER_CODE` (selectable, monospace digits), placed date; `District` name only (never the street); the five-step stepper (reuse of `OrderStepper`, customer variant, design-system part 8: steps `T_STEP_RECEIVED`, `T_STEP_PROCESSING`, `T_STEP_SCHEDULED`, `T_STEP_DELIVERING`, `T_STEP_FINISHED`); date block: the requested date and slot as `T_REQUESTED`; from step 3 the expected date `T_EXPECTED` with the fixed note `T_EXPECTED_MAY_MOVE` (it may move); cake lines (`T_CAKE_LINE`: name and quantity, one line per cake) and `T_CAKES_TOTAL`; fee block [v1.1 | 2026-11-02] (api/10 v1.3: `amount_to_collect_vnd` is null until the final fee is known; the client never sums anything and never shows the estimate as an amount to collect). Four states: (1) fee unknown (`delivery_fee_final_vnd` null, amount null): `T_CAKES_TOTAL` with the subtotal, `T_FEE_ESTIMATE_LINE` (estimate, muted) with the note `T_FEE_REAL_AT_DELIVERY`, and in place of a total the line `T_TOTAL_PENDING` ("the fee will be confirmed"); no total row, no sum, no total number anywhere; (2) fee known: `T_CAKES_TOTAL`, `T_FEE_FINAL` with the real fee, `T_TOTAL_COLLECT` with `amount_to_collect_vnd` from the server; (3) fee known as 0: `T_CAKES_TOTAL`, `T_FEE_FREE` in place of the fee amount, `T_TOTAL_COLLECT` equal to the subtotal (server value); (4) fee corrected: same as (2) or (3) with the latest amount, replaced in place on refresh, no history, no "corrected" label. The estimate line disappears once the real fee is known. The state is chosen only by whether the server amount is null, never by status step.
- Cancelled card: badge `T_STATUS_CANCELLED`, no stepper, no reason, no fee block; the shop contact `T_CANCELLED_CONTACT` with two actions `T_CALL_SHOP` and `T_ZALO_SHOP` (numbers from the catalog contact, native phone and Zalo link).
- Finished card: all five steps done, the real fee and amount to collect remain visible [v1.1 | 2026-11-02] (a finished order always has a final fee; if the server still sends null, state 1 applies, never a computed total). [v1.0 | 2026-11-02] The screen never states how many days an old order stays visible (owner decision; `T_FINISHED_NOTE_30` removed). Under the list a neutral line `T_OLDER_MAY_HIDDEN` says an older order may no longer be shown (with shop contact), shown with the list end whenever the list has at least one finished or cancelled card.
- Empty (no orders, or a number that never ordered): the same screen and the same text for both, `T_EMPTY_TITLE` and `T_EMPTY_BODY` ("Không tìm thấy đơn nào cho số này gần đây"), with the shop contact and a `PrimaryButton` `T_ORDER_NOW`. The text never says the number is or is not a customer, never suggests a typo of a known number, and the layout and animation do not differ from a result. [v1.0 | 2026-11-02] The server owns the response time floor; the client adds no minimum spinner time.
- Rate limit (429 `RATE_LIMITED`): `InlineMessage` Warning `T_ERR_RATE` with the wait from `Retry-After` shown as minutes and seconds (`{wait}`), the submit and pull-to-refresh are disabled with a live countdown, no mention of which limit applied; the same text appears whether the phone has orders or not.
- Loading: card skeletons (3), stepper skeleton inside. Error (network or 5xx): `T_ERR_GENERIC` and `T_RETRY`; page 2+ errors keep the loaded pages. Offline: `T_OFFLINE` banner; earlier loaded results stay on screen as read-only with `T_STALE_AS_OF`; refresh disabled. Invalid cursor (422): reload page 1 silently once, then `T_ERR_GENERIC`.
- Disabled: submit during a request. Success: the list.
- Motion: step change after refresh animates the stepper marker with the standard spring, fade only under reduced motion. Haptics: none on lookup, light impact on the pull-to-refresh release (native).
- Portrait and landscape: honestly no structural difference; in landscape the cards are limited to the readable width (about 600 dp, centred) and the list scrolls; the phone field and button stay above the keyboard.
- Native base: iOS `List` with `refreshable`, `ContentUnavailableView` for empty and error (iOS 17, no `#available`); Android `LazyColumn` with `PullToRefreshBox` and Material 3 cards. Liquid Glass applies only to the system bar and sheets, not to the cards (content layer stays opaque for reading).

## Security notes for the design (to scribe and atlas)

- The phone is submitted in the request body, never kept in navigation state, logs or deep links. No deep link opens S-11 with a phone.
- Because anyone knowing a phone can see its orders (accepted in ADR-0034), the card shows district only and masked phone. [v1.0 | 2026-11-02] The owner decided that order code and cake names with quantities are shown; the earlier business question is closed.
- Date window [v1.0 | 2026-11-02]: the "today + 7" window belongs to the server (`expected_date_range` in the answers, API 09); the tracking screens only display `expected_delivery_date` and never compute a range.
