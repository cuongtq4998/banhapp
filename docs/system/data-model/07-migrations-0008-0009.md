# Data Model: migrations 0008 and 0009 (split, order of application)

Part of [data-model.md](../data-model.md). Version 1.0 [v1.0 | 2026-11-02]. Traces: ADR-0033, ADR-0034, rule 15.1 (data-model/05), project rule of 200 lines per file (owner decision of 2026-11-02: it applies to SQL migrations).

## 1. Split by responsibility [v1.0 | 2026-11-02]

The single file described in data-model/06 section 3 (233 lines) is two numbered files. Forward-only; neither file is edited after it was applied anywhere.

| File | Content | Transaction |
| ---- | ------- | ----------- |
| `0008_order_process.sql` | Count rows; drop the old guard and capacity triggers, the `status` CHECK and `customer_order_open_idx`; add the three columns; remap `customer_order.status` (New to Received, Confirmed to Processing, Completed to Finished); backfill the final fee of `Finished` rows; default `Received`; new CHECKs; index `customer_order_open_list_idx`; its own verify block (counts, no old status) | 1 |
| `0009_order_process_records.sql` | Tables `order_expected_date_change` and `order_fee_correction` with indexes and CHECKs; function `order_record_insert_only` and its two triggers; recreated guard, capacity release and immutable trigger functions; its own verify block | 2 |

Each file is one transaction; the two together are not atomic.

## 2. Order of application and deploy rule

1. Operator takes the `pg_dump --format=custom` (rule 15.1, last migration `0007`) and test-restores it once.
2. The old backend is stopped (statuses change; old and new code never run together). The runner applies `0008`, then `0009`, in number order.
3. The deploy starts the new backend only after both succeeded and the checks of section 4 passed.
4. If either file fails, the deploy stops there, the new backend is not started and the release is not promoted.

## 3. State if 0009 fails (0008 committed)

Statuses are already remapped to the six names; the new columns and CHECKs are in place; `customer_order_open_idx` is gone; the triggers are the old ones or missing: 0008 drops `customer_order_status_guard` and `customer_order_release_capacity` and only 0009 recreates them, and the old guard knows only the old words. Status changes are then unguarded, a cancel releases no capacity and writes no event. The old backend does not understand the new words and the new one must not run: the system is unusable, there is no partial service, and no order may be taken in this state.

Recovery is the `pg_restore` of the `pg_dump` taken first (section 2 step 1), then the old backend is started. The failed file is fixed in a new commit and the whole sequence is run again from a fresh dump. Do not patch the live database by hand and do not edit an applied file (if both files already applied on another environment, the fix there is a new numbered file). There is no down script.

If 0008 fails: its transaction rolls back, the database is as before; start the old backend, no restore needed.

## 4. Checks to run after both

- No `customer_order.status` outside the six names; the `customer_order` row count equals the count taken before 0008.
- Both tables exist with their CHECKs and indexes; both insert-only triggers exist; `customer_order_status_guard`, `customer_order_release_capacity` and `customer_order_immutable` exist on `customer_order`.
- `customer_order_open_list_idx` exists and `customer_order_open_idx` does not.
- Smoke through the app path (staging): a test order goes Received, Processing, DeliveryDateScheduled (date set), DeliveryStarted (fee set), Finished; a cancel releases capacity and writes an `order_event`; an UPDATE of an `order_expected_date_change` row is refused.
- `GET /healthz?deep=1` is green; the counter `lookup_floor_exceeded` stays 0 for a lookup of a fake phone.
