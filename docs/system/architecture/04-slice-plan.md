## 11. Slice Plan [v1.1 | 2026-10-25]

Order of end-to-end slices. A slice is done when its acceptance criteria pass on both apps and the backend, with contract fixtures in `contracts/fixtures/` agreeing across the three test suites. Each slice is a pull request (or a short series) that touches every component listed; the contract is fixed in api.md and data-model.md before the slice starts. Nothing in a later slice is needed to test an earlier one.

Parallel work inside a slice: backend and the two apps start together from the contract and fixtures; the apps may use fixtures as a stub server until the backend endpoint lands. Slices 1 and 2 may overlap on the apps once slice 0 is done, but slice 3 waits for slice 2 on the backend (availability and capacity reads feed the order check). Structure note [v1.8 | 2026-10-27] (ADR-0018 v2.0, ADR-0007 v1.5): there is no calendar of package extractions; a module or package split happens only when a trigger of ADR-0018 fires, never because a slice starts. What each slice must respect instead: iOS builds the order flow as MVVM-C (coordinator, `Route` enum, `@Observable` view models; section 15) inside the existing app target and adds the import-direction script with the next iOS change; Android builds the order flow as MVI with one `OrderFlow` store scoped to the order navigation graph (section 15) after removing the design-to-app couplings and adding the JUnit import test; backend lands `DomainError` and the layering test (which also fails on unknown top-level folders) before slice 3. Every hand-written file, source and document, stays at 200 lines or fewer, so slice work splits files by responsibility first.

Testers write each slice's test cases from its acceptance criteria and the fixtures before development ends.
